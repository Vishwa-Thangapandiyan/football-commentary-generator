## The demos, in the order I'd present them

### 1. VIDEO + LIVE COMMENTARY  ★★ the one to show her

```powershell
python demo_app.py
```

Opens http://127.0.0.1:8000. Wait ~30 s for "Video demo ready" (it loads the model
and does a warm-up decode), then the browser opens.

**The match plays on the left. As the playhead reaches each detected event, your
Transformer generates that line and it appears in the feed on the right**, with the
real server-side generation time shown in milliseconds (~60 ms for a corner,
~750 ms for the goal).

Use the **"Jump to the GOAL"** button to go straight to 29:20 — that's the moment
worth showing. "Reset feed" clears it so you can replay.

**What to say:** *"Action spotting ran once over the half when I launched this — it's
a batch model, not streaming. But every commentary line is generated by my
Transformer at the moment the video reaches that event. The millisecond timing is
real decoding, not playback."*

If she asks whether the text is stored: press Reset, replay, and the same lines are
regenerated with fresh timings. Greedy decoding is deterministic, so identical text
with different latency is exactly what a live model looks like.

Shows Goal + Corners only (the classes that read cleanly without a player).

**"Generate Variation" button** (under each commentary line): resamples that same
event with `torch.multinomial` at temperature 0.9 / top-p 0.9 and a fresh random
seed. Useful when several corners in a row produce the same greedy sentence.

*What to say:* *"The automatic line is greedy decoding - deterministic. This button
samples from the same learned distribution instead of taking the argmax, so you get
a different phrasing the model also considered likely. The grounding mask still
applies, so it still cannot invent a player."*

Do **not** claim the variation proves the system is live - the millisecond decode
timing already does that. Variation is presentation polish only.

### 2. JSON → COMMENTARY  ★★ the one that shows the data flow

```powershell
python demo_json.py
```

Opens http://127.0.0.1:8010 (different port from demo_app, so both can run).
Type or edit a JSON event, press **Generate Commentary**. Presets available for a
goal, a corner, a card and a multi-event timeline.

**This is your best slide for explaining the architecture** — it shows the exact
`structured_input` string fed to the encoder, and the grounding map (tag -> real
name), so you can trace: *your JSON -> structured representation -> Transformer ->
tagged output -> names substituted back*.

**Generate Variation** re-runs the same event with torch.multinomial sampling
(T=0.9, top-p=0.9, fresh seed). On a goal with two players this produces genuinely
different, correctly-grounded lines.

`minute` is minutes **within a half** (max 54 in training), not absolute match
time. A 90th-minute event is `half: 2, minute: 45`. Entering 90 returns a
clear 400 error rather than nonsense.

### 3. The pipeline in the terminal — shows the plumbing

```powershell
python spot_to_commentary.py --threshold 0.35
```

Takes ~1 min (TensorFlow loads the spotting model). Prints, for each detected event:
the timestamp, the spivak class + confidence, the structured input, and the
commentary your Transformer generated.

**What to say:** *"The only input is the video's frame features. A pretrained action
spotting model finds the events, we convert each into our structured format, and our
Transformer generates the commentary. Nothing is looked up."*

**Point at the goal:** `[29:20] Goal conf=0.90`. The ground-truth annotation says
29:51, but the broadcast scoreboard shows 1-0 by 29:56 — the detector is arguably
more accurate than the caption timestamp, which is when the *commentary* was written.

Only Corner and Goal read cleanly (see Known limitations). To show only those:

```powershell
python spot_to_commentary.py --only soccer-ball,corner
```

Do **not** try to filter cards out with `--threshold` — a yellow card at 0.67
outranks a good corner at 0.62, so no threshold separates them.

### 4. The event browser — pick any of 7,826 test events

```powershell
python demo_live.py
```

Opens http://127.0.0.1:8000. Pick any event from the dropdown, press **Generate**.
Shows encoder input, grounded players, raw model output, restored commentary, and the
human reference. Ctrl+C in the terminal to stop.

**What to say:** *"Player names are never in the model's vocabulary. It emits
`<PLAYER_1>` slots that are filled in afterwards, so it cannot invent a player."*

If asked whether it's canned: it's greedy decoding, so the same event always gives
the same sentence. That is determinism, not a lookup table. The proof is that any
event works, not that the wording changes.

## If you're asked to prove the anti-hallucination claim

```powershell
python test_grounding.py --ckpt checkpoints/full_best.pt --data data/processed.json --n 200
```

Prints 5 checks and `GROUNDING GUARANTEE: VERIFIED`. The one to point at is the
**adversarial** test: every banned player tag is forced to a +1e9 logit — the model
maximally "wants" to emit an ungrounded player — and it still cannot, because the
mask sets those logits to -inf before the argmax. It's structural, not learned.

## Known limitations — say these before you're asked

1. **Player identity cannot come from video.** No jersey OCR or roster linkage, so
   pipeline-generated commentary has no player names. Next phase.
2. **Card and substitution text breaks without a player** — "the referee gives a
   yellow card to." Use `--only soccer-ball,corner` so these never appear on screen.
3. **All corners generate identical text.** Small model, templated corpus.
4. **The goal line invents a free kick.** Scorelines and some details are
   ungrounded — a *content* hallucination, a different class from the *identity*
   hallucination the system does prevent.
5. **`<no_event>` mode-collapses** — four different situations all produced "is
   adjudged offside", which is why highlights mode uses labelled events only.
6. **Not arbitrary video.** SoccerNet's precomputed ResNET features only exist for
   their matches. A new video would need its own feature extraction.

## What NOT to claim

- Do **not** say YOLO identifies players. It detects *people*, nothing more.
- Do **not** say the system works on any uploaded video (see limitation 6).
- Do **not** present the spivak model as yours — it's Yahoo's pretrained
  action-spotting model, CC-BY-4.0. Yours is the Transformer.

## Troubleshooting

| Problem | Fix |
|---|---|
| Port 8000 busy | Only run ONE of `demo_app.py` / `demo_live.py` at a time, or edit `PORT` |
| `demo_json.py` rejects minute 90 | Correct - minute is within-half (0-60). Use half 2, minute 45 |
| Video won't play / won't seek | `outputs/web/half1.mp4` missing — `demo_app.py` re-creates it via ffmpeg on start |
| First commentary is slow | Warm-up runs at startup; wait for "Video demo ready" before presenting |
| Browser doesn't open | Type http://127.0.0.1:8000 yourself |
| TensorFlow prints red `remapper failed` warnings | Harmless — inference still runs |
| `spot_to_commentary.py` slow to start | Normal, TF loads the SavedModel (~30–60 s) |
| Anything at all fails | Fall back to `outputs\demo_sidebyside.mp4` |

**Do not run `train.py`.** It would overwrite `checkpoints/full_best.pt`.
